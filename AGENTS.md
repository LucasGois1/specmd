# Guidance for agents

## Repository state

SpecMD is an assistant plugin for coding agents (Claude Code and Codex). It keeps the canonical Markdown documentation, with embedded Gherkin scenarios, aligned with the software. The developer defines the rules by talking with the agent. The plugin runs deterministic checks at key moments and sends feedback back to the agent: documentation without scenarios, new scenarios the developer has not seen yet, scenarios without an implementation or failing.

The direction changed on 23/10/2026 ([D-021](docs/decisions.md)): the signed acceptance cycle, the authority, the trust and the implementation blocking were removed. See [docs/implementation-status.md](docs/implementation-status.md) for what exists today. [HANDOFF.md](HANDOFF.md) preserves the earlier context and is partly superseded. Prototypes in `research/` do not constitute production support.

When reporting checks, state only what was actually run and its scope. Never fabricate test runs or integration support.

## Core design rules

- Markdown is the canonical source of the business rules. Requirements and their scenarios live in the same document.
- The solution must not require `.feature` files, nor their generation as a run step. Scenarios are read from the Markdown and run in memory.
- The plugin helps and does not get in the way: it sends objective feedback back to the agent and never ends the session. Repeated feedback without any change lets the agent stop.
- The developer's confirmation is a normal reply in the conversation. New or changed scenarios must be shown to the developer before implementation.
- A code change renews the run of the scenarios. Local state (`.specmd/local/`) is rebuildable and can be deleted.
- Available hooks must be verified per platform and version. Do not invent event or API names as if they were confirmed.
- Both hosts use a single `hooks/hooks.json`; Claude Code loads it by default from the plugin root. Do not declare a second hooks file.
- The plugin bundle is versioned in `codex-plugin/` and is generated by `scripts/build_codex_plugin.py`; when you change `src/`, `scripts/`, `hooks/`, `commands/`, `skills/`, `vendor/` or the manifests, generate it again and commit it together (CI checks it with `--check`). Do not edit `codex-plugin/` by hand.
- The plugin's runtime dependencies live in `vendor/`, generated by `scripts/vendor_deps.py` from `pylock.toml`. Do not edit `vendor/` by hand; when dependencies change, regenerate the lock and `vendor/`.

## Working on the documents

- Write in English; preserve stable identifiers and relative links.
- Keep requirements and their scenarios in the same Markdown.
- Use English Gherkin in examples.
- Record normative changes and decisions visibly in [docs/decisions.md](docs/decisions.md).
- Mark commands, schemas and flows not yet implemented as proposals.
- Do not add licenses or policies as if they had already been chosen.
