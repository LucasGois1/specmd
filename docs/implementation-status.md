# Implementation status

Version 0.3.0, after the change of direction [D-021](decisions.md): SpecMD is an assistant that sends deterministic feedback back to the agent. The signed acceptance cycle, the authority, the trust, the browser review, the protected `verify` and implementation blocking were removed.

| Area | Implemented | Limit |
| --- | --- | --- |
| Discovery | Every Markdown file in the project, including unversioned ones, except what Git ignores, the common project files (README, CHANGELOG, LICENSE, AGENTS, CLAUDE, `.github/`) and the optional `.specmdignore`; optional front matter; per-document hashes and a fingerprint of the requirements and scenarios (`spec_fp`). | `.specmdignore` implements a subset of the `.gitignore` patterns (no `[...]` classes). |
| Gherkin | Fenced blocks; requirement with a free-prefix ID in the heading; scenario linked to the requirement by position or by tag; automatic ID `path::name` or a `…-SCN-…` tag; `Rule` and `Scenario Outline`; `gherkin_language`; `@wip`. MDG (`*.feature.md`, [SMD-REQ-031](requirements.md)) converted into Gherkin in memory, line by line, with a `Rule` with an ID as a requirement. The Java and Go bridges receive the configured language as a `# language:` header in the text. | In MDG, the language header for the bridges needs a free line at the top; SpecMD moves the `Feature` heading down one line when the next line is empty. |
| Hooks | `SessionStart` (summary and conventions), `UserPromptSubmit` (scenarios seen by the developer), `PostToolUse` (documentation gaps after the edit), `Stop` (gaps, scenarios awaiting the developer, run after a code change). | Native dispatch observed in Claude Code in headless mode ([evidence](../research/claude/README.md)) and in Codex 0.163 with `gpt-6-luna`, including the `Stop` block ([evidence](../research/codex/native-session.md)). In Codex, the plugin is enabled per user and updating it requires trusting it again in `/hooks`. `SPECMD_HOOK_LOG` records each hook response, for hosts that do not show them. The project root comes from `CLAUDE_PROJECT_DIR` or from the hook process's directory, never from paths in the payload. |
| Feedback | Scenario, step, line, error message and a ready-made snippet for steps without an implementation. The same feedback repeated or four blocks let the agent finish; internal errors become warnings. | Messages in English (default) or Portuguese (`language = "pt"`, [SMD-REQ-032](requirements.md)); no other language. |
| Confirmed scenarios ([SMD-REQ-028](requirements.md)) | `UserPromptSubmit` stores the scenarios and requirements as of the developer's message (`.specmd/local/prompt-scenarios.json`) and the code state. Removed or renamed scenario, changed `Then` or `Given`/`When`, changed table, added `@wip` and removed requirement go to the agent after the edit and to the developer on finishing. It is sent back to the agent once when a scenario that was failing had its `Then` changed together with the code in the turn. | A scenario renamed without an ID tag shows up as removed; the developer's confirmation is not detected, so the summary shows up even when the developer asked for the change. |
| Ignored documents ([SMD-REQ-029](requirements.md)) | Read lightly, with cache: a `…-REQ-…` heading, a Gherkin block or a heading with a Gherkin keyword in any language (MDG). Warns the agent when one of them changes and starts having one of these elements. | Notice only; does not block on finishing. |
| Legacy adoption ([SMD-REQ-030](requirements.md)) | `/specmd:adopt` and `specmd adopt`: analyzed documents without scenarios and requirements without a scenario, in path order. The command guides the agent to separate with the developer what goes into `.specmdignore` and to handle one document at a time. `.specmd/local/scenario-history.json` stores the scenarios that have already passed. The failure comes with the divergence guidance when the scenario never passed and the product functions it executes did not change in the session (version at session start read from Git); when a scenario that already existed breaks because the agent changed those functions, the feedback guides the agent to update the scenario or adjust the code. | Conducting the adoption (list to the developer, one document at a time, asking about divergences) depends on the agent following the command; the plugin only provides the list and the feedback. |
| Run | Python/Behave in a subprocess with the project's interpreter when it has `behave`, loading `environment.py`; Java (Cucumber-JVM) and Go (Godog) bridges through the JSON protocol, with scenarios matched by origin. | Java/Go reject `Rule`/`Outline` and do not skip `@wip` scenarios; `behave.ini` is not read. |
| State | `.specmd/local/state.json` with the last run, seen scenarios and the count of blocks; atomic write with a lock. The code state is a Git snapshot (current commit and content of the files that differ from it): committing or undoing a change does not count as a change. | POSIX only (uses `fcntl`). Without Git, a scan of the metadata says only whether something changed, not what. |
| Performance ([D-022](decisions.md)) | Per-document analysis cache in `.specmd/local/inspection-cache.json`: an unchanged document is neither reread nor reanalyzed. `PostToolUse` skips the analysis when the edit tool reports a file that is not Markdown nor `.specmdignore`, `specmd.toml` or `.gitignore`. `scripts/benchmark.py` (`make bench`) measures the hooks in a synthetic repository. | Measured on a Mac with 5 thousand documents and 50 thousand files (p50): `PostToolUse` 73 ms after editing code, 276 ms after Bash and 314 ms after editing a document; `UserPromptSubmit` 268 ms; `Stop` without a code change 397 ms; `SessionStart` 412 ms, or 2.3 s without cache. Before: 7 to 9 s per hook. |
| Affected scenarios ([SMD-REQ-027](requirements.md)) | With Python 3.12+, the Behave worker records per scenario the project functions executed (`sys.monitoring`), the files read and whether it started a process or opened a connection. `Stop` and `specmd run --affected` run only the scenarios that executed a changed function, read a changed file, are new or changed, were failing or never ran; `specmd run` runs all of them. Coverage in `.specmd/local/coverage.json`, with a hash per function (the module level separately). | Runs all of them when the module level of a used file changes, or the steps, `environment.py` or the configuration (`specmd.toml`, `pyproject.toml`, lock files) change, and without coverage: Java, Go, a runner with its own `command`, Python earlier than 3.12, no Git. Dependencies outside the Python code (environment variables, database, listed directories) are not seen. `make bench` with `--rules 3000` (trivial scenarios): 4.9 s for all of them and 0.56 s after changing one function, with 1 scenario run. |
| CLI | `init`, `inventory`, `check`, `run`, `demo` and the hook adapters; `scripts/specmd_cli.py` runs the CLI through the plugin. | — |
| Installation | Marketplace at the repository root (`.claude-plugin/marketplace.json`, plugin `./`). Installing with `/plugin install specmd@specmd` at project or local scope already activates the repository, without `specmd.toml`; `specmd init` (or `/specmd:init`) merges `extraKnownMarketplaces`/`enabledPlugins` into `.claude/settings.json` for the team; default Python runner through `tests/steps`/`features/steps`/`steps`; local state that ignores itself in Git; dependencies bundled in `vendor/` and a bootstrap that looks for Python 3.11+; a skill with the conventions; `make agent` to test in the session only. In Codex, the `specmd` marketplace (`.agents/plugins/marketplace.json`) points to the versioned bundle in `codex-plugin/`, so `codex plugin marketplace add LucasGois1/specmd` and `codex plugin add specmd@specmd` install from GitHub; CI checks the bundle against the sources. `specmd init` also enables the plugin in the project's `.codex/config.toml`, which activates SpecMD in Codex without `specmd.toml`. | Automatic loading after the trust dialog follows the Claude Code documentation and has not yet been exercised in an interactive session. No Windows. |

## Validations

The local suite (`python -m unittest discover -s tests`) runs on macOS and in CI on Ubuntu and macOS. The hook tests use real projects created by `specmd demo` and actually run Behave; the hook payloads are simulated.

The evidence in [research/claude](../research/claude/README.md) records headless Claude Code sessions with a real model exercising documentation, code that contradicts the documentation and the implementation of confirmed scenarios. The trust dialog, the interactive UX and a real developer answering the agent were not exercised there.

Green tests do not prove that the scenarios represent the developer's whole intent nor that the assertions are strong; the documentation and the steps still need human review, usually in the PR.
