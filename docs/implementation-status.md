# Estado de implementação

Versão 0.3.0, depois da mudança de direção [D-021](decisions.md): o SpecMD é um assistente que devolve feedback determinístico ao agente. O ciclo de aceite assinado, a autoridade, o trust, a revisão no navegador, o `verify` protegido e o bloqueio de implementação foram removidos.

| Área | Implementado | Limite |
| --- | --- | --- |
| Descoberta | Todo Markdown do projeto, inclusive não versionado, menos o ignorado pelo Git, os arquivos de projeto comuns (README, CHANGELOG, LICENSE, AGENTS, CLAUDE, `.github/`) e o `.specmdignore` opcional; frontmatter opcional; hashes por documento e impressão digital dos requisitos e cenários (`spec_fp`). | O `.specmdignore` implementa um subconjunto dos padrões do `.gitignore` (sem classes `[...]`). |
| Gherkin | Blocos cercados; requisito com ID de prefixo livre no título; cenário ligado ao requisito pela posição ou por tag; ID automático `caminho::nome` ou tag `…-SCN-…`; `Rule` e `Scenario Outline`; `gherkin_language`; `@wip`. MDG (`*.feature.md`, [SMD-REQ-031](requirements.md)) convertido em Gherkin em memória, linha a linha, com `Regra` com ID como requisito. Os bridges Java e Go recebem o idioma configurado como cabeçalho `# language:` no texto. | No MDG, o cabeçalho de idioma para os bridges precisa de uma linha livre no topo; o SpecMD desce o título `Funcionalidade` uma linha quando a seguinte está vazia. |
| Hooks | `SessionStart` (resumo e convenções), `UserPromptSubmit` (cenários vistos pelo dev), `PostToolUse` (pendências de documentação após a edição), `Stop` (pendências, cenários aguardando o dev, execução após mudança de código). | Dispatch nativo observado no Claude Code em modo headless ([evidência](../research/claude/README.md)); no Codex, os eventos novos não foram exercitados nativamente. A raiz do projeto vem de `CLAUDE_PROJECT_DIR` ou do diretório do processo do hook, nunca de caminhos do payload. |
| Feedback | Cenário, passo, linha, mensagem de erro e trecho pronto para passos sem implementação. Mesmo feedback repetido ou quatro devoluções deixam concluir; erros internos viram aviso. | Mensagens em pt-BR. |
| Cenários confirmados ([SMD-REQ-028](requirements.md)) | O `UserPromptSubmit` guarda os cenários e requisitos da mensagem do dev (`.specmd/local/prompt-scenarios.json`) e o estado do código. Cenário removido ou renomeado, `Então` ou `Dado`/`Quando` alterados, tabela alterada, `@wip` adicionado e requisito removido vão para o agente após a edição e para o dev ao concluir. Volta ao agente uma vez quando um cenário que falhava teve o `Então` alterado junto com o código no turno. | Cenário renomeado sem tag de ID aparece como removido; a confirmação do dev não é detectada, então o resumo aparece mesmo quando ele pediu a mudança. |

| Adoção em legado ([SMD-REQ-030](requirements.md)) | `/specmd:adopt` e `specmd adopt`: documentos analisados sem cenários e requisitos sem cenário, em ordem de caminho. O comando orienta o agente a separar com o dev o que vai para o `.specmdignore` e a tratar um documento por vez. `.specmd/local/scenario-history.json` guarda os cenários que já passaram; falha num cenário que nunca passou traz a orientação de divergência. | A condução (lista ao dev, um documento por vez, perguntar em divergências) depende do agente seguir o comando; o plugin só fornece a lista e o feedback. |
| Execução | Python/Behave em subprocesso com o interpretador do projeto quando ele tem `behave`, carregando `environment.py`; bridges Java (Cucumber-JVM) e Go (Godog) pelo protocolo JSON, com cenários casados pela origem. | Java/Go recusam `Rule`/`Outline` e não pulam cenários `@wip`; `behave.ini` não é lido. |
| Estado | `.specmd/local/state.json` com última execução, cenários vistos e contagem de devoluções; escrita atômica com lock. O estado do código é um snapshot do Git (commit atual e conteúdo dos arquivos que diferem dele): commitar ou desfazer uma mudança não conta como mudança. | Apenas POSIX (usa `fcntl`). Sem Git, uma varredura dos metadados diz só se algo mudou, não o quê. |

Antes: de 7 a 9 s por hook. |
| Cenários afetados ([SMD-REQ-027](requirements.md)) | Com Python 3.12+, o worker do Behave registra por cenário as funções do projeto executadas (`sys.monitoring`), os arquivos lidos e se iniciou processo ou abriu conexão. O `Stop` e `specmd run --affected` executam só os cenários que executaram uma função alterada, leram um arquivo alterado, são novos ou alterados, falhavam ou nunca rodaram; `specmd run` executa todos. Cobertura em `.specmd/local/coverage.json`, com hash por função (o nível do módulo à parte). | Executa todos quando muda o nível do módulo de um arquivo usado, os passos, o `environment.py` ou a configuração (`specmd.toml`, `pyproject.toml`, arquivos de lock), e sem cobertura: Java, Go, runner com `command` próprio, Python anterior a 3.12, sem Git. Dependências fora do código Python (variáveis de ambiente, banco, diretórios listados) não são vistas. `make bench` com `--rules 3000` (cenários triviais): 4,9 s para todos e 0,56 s após mudar uma função, com 1 cenário executado. |

## Validações

A suíte local (`python -m unittest discover -s tests`) roda no macOS e no CI em Ubuntu e macOS. Os testes de hooks usam projetos reais criados por `specmd demo` e executam o Behave de verdade; os payloads dos hooks são simulados.

A evidência em [research/claude](../research/claude/README.md) registra sessões headless do Claude Code com modelo real exercitando documentação, código que contraria a documentação e implementação de cenários confirmados. O diálogo de confiança, a UX interativa e um dev real respondendo ao agente não foram exercitados ali.

Testes verdes não provam que os cenários representam toda a intenção do dev nem que as asserções são fortes; a documentação e os passos continuam precisando de revisão humana, normalmente no PR.
